# 任务记录、算力累计与交付归档

## 一次记录，生成三个视图

在本任务目录维护`task-record.json`作为本次事实主记录。只更新新发生的提交、结果、费用证据和审核结论，不在进度、算力和交付文档各自重填同一金额。此前已有人工账本时保留历史，先核对唯一任务身份再引入主记录，不自动把旧任务当新任务导入。

写入前重新读取主记录并核对读取时的版本或SHA256；变化时合并最新事件，不能用旧副本覆盖。主记录只由一名写入者维护；经校验后写同目录随机临时文件，再原子替换，保留历史备份。版本检查本身不等于跨进程锁，多个写入者须串行协调。各色汇总表从`tasks`最新事实派生，不让旧“未提交”行覆盖已受理任务。

用 [render_task_record.py](../scripts/render_task_record.py) 一次输出`执行进度.md`、`算力消耗明细.md`、`交付摘要.md`和`summary.json`到新快照目录。当前任务根目录的进度可保留当前快照链接及新增事件，不能用渲染器覆盖用户原有日志。各阶段说明引用本次审核记录和费用快照，避免维护多个独立金额副本。

提交受理后立即写身份/参数/预计点数，下载完成、审核/合音完成时合并增量；状态没变化不改账本或渲染报表。首次交付生成一次统一入口，后续只随新事实更新。结构化审核结论附输入SHA256，由唯一写入者合并；不同代理不各写累计或“最新入口”。

```powershell
python -X utf8 "<skill>/scripts/render_task_record.py" --record "<任务目录>/task-record.json" --out "<任务目录>/记录快照01"
```

主记录字段：

- `identity`：必填`source_video`、`product`、`canvas`；可补明确的下载/最终交付目录，依当前用户要求。
- `tasks`：每项`submitted`是布尔值，`stage`为字符串`480`/`1080`/`other`；已提交任务需`task_id`，暂取不到时用`node_id`与`submitted_at`。重复身份会拒绝，不把下载副本、静音预览和原音版添加成平台任务。
- 实际参数写`setting/model/quantity/expected_points`，未知金额用`null`；提交时间建议北京时间带时区。实际提示词、材质依据、引用图序及参数截图另存对应路径，也可补进JSON备注；渲染器仅展示支持的字段，不替代完整证据。
- `debit/refund`配`cost_verified:{"debit":true,"refund":true}`及`cost_evidence:{"debit":"账单路径","refund":"退款状态证据路径"}`。仅明确核实且对应证据文件存在的金额加入已核实小计；0退款也不能凭猜测填写。路径相对JSON目录解析，工具只看文件存在，账单内容由执行者核实。
- `review:{"verdict":"通过/有瑕疵/不通过/未审核","evidence":"检查记录路径"}`及`file`记录本次实际结论和文件。1080优先用`parent480`填真实480任务ID；暂取不到平台ID时可填`parent480_key`（渲染器生成的`task:ID`或`node:节点|提交时间`）。旧`parent480`中的节点名仅在对应480唯一、同商品/颜色且有通过证据时回退；节点复用有歧义仍警告，不补造平台ID。缺少有证据的已通过480时会保留实际历史并提示矛盾，不能自动进入1080或补造480。
- 每任务可有`audio`，多款色应分别记录原音、原声预览及听审证据，顶层`audio`保留兼容单任务。技术合音/动作同步与听感语义分开；不能把技术成功写成听审通过。
- `audio:{"source":"本次配套原音路径","file":"最终原声版路径","review":{"verdict":"未审核","evidence":null}}`记录本地原音阶段；听审后再填写实际结论。工具不会自动判断是否合格，也不会仅因成片存在就生成“已完成”。

- `generation_policy`只记录本任务当前授权与限制，不能由画面通过推导新生成授权；建议记用户原话、生效时间、去重范围、1080/重试许可及允许首次款色。提交前重读最新主记录；受理未知也占用该款色，查明原任务前不再按生成。

所有生成报告都是记录快照，不能拿工具的“未发现矛盾”代替授权、时序检查和审核通过；仍要核对480审核发生在1080提交前，以及输出是否属于同一批素材。

## 每次生成的算力点数与累计

- 在原视频/执行包目录维护一份 `算力消耗明细.md`；每个实际提交的平台任务一行，以任务ID为准，无法取得任务ID时记录节点ID和提交时间。480、1080、经授权的重试、误提交及失败任务都保留，不因失败或未下载而漏记。同一任务的轮询、下载、副本和本地合音不重复计费。
- 每笔记录北京时间、货号/阶段、任务或节点ID、模型/实际清晰度/数量、提交时预计点数、已核实实扣、已核实退款、净消耗、费用状态及账单/截图证据。未提交的方案预估单列，不加入已提交任务预计合计。
- 预计点数不是实际消耗。优先以平台账单/消耗明细核实实扣；余额差仅在能排除其他任务、充值及退款时作为辅助，不能因余额暂未变化就记“0点”或“免费”。失败不等于退款，退款也需证据。
- 每次任务终态更新该行并重新相加：已提交任务预计合计、已核实实扣小计、已核实退款小计和净实际总额（实扣减退款）。有待核验的扣费或退款时，明确“净实际总额未确认”并列待核验笔数，不把未知当0，也不将预计和实扣相加。账单补齐后更新原行，不能新增一笔造成重复累计。
- `执行进度.md`、成片同名说明和最终回报均写“本次预计/实扣/退款/净消耗＋本项目累计”，未知项明确标注。仅维护流程时补文档，不触发真实生成。


## 下载、同目录归档与备注

本用户当前交付布局采用`原视频`、`要看的视频`（480）、`1080视频`、`其他资料`。前三个只放视频，说明/费用/截图/审核/原下载/历史集中`其他资料`，不在日期根散落多个入口。其他任务明确指定布局时从其要求。单条已准备好就可先归档，最终集中汇总一次；相同哈希不重新复制。

`finish_downloads.py`只产待审证据及配原音核看片，不改主记录或自动合格交付。商品、动作同步及听审仍需显式合并，已有技术产物不因交接重做。

- 在结果节点使用已验证的“下载到本地”，默认指向 **原视频文件的父目录**。用户当前明确指定执行包或其他交付位置时，以该目录为准并记录与源片的关系。用户指定每日日期目录时，按任务约定的日期依据和时区归档（本批为实际生成日、北京时间M月D号），分别保留提交、完成和下载时间；跨日下载不擅改生成日期归属，不能依本机其他时区归错日期。原下载、原声版和审核证据分开放并保留对应关系；不要自行改去商品图目录或只留临时outputs。原视频路径是目录输入时先解析实际MP4再取其父目录。archive_result.py始终按传入source-video的父目录归档，例外目标需单独正确处理，不能伪造source-video去改变脚本目标。
- 归档文件名示例：`原视频名__货号-颜色__测试01__480原生__20261114-160000.mp4`。复测用测试02等；高画质结果按真实阶段/参数标注。避免仅叫“视频01.mp4”；长原名可截短，保留货号、阶段、清晰度和时间。
- 1080文件示例：`原视频名__货号-颜色__正式01__1080__20261114-161000.mp4`；说明中写对应的480测试文件/批次、通过结论，以及1080独立复核结果。原视频、480片和1080片分别保留。
- 最终原声版示例：`货号-颜色__正式01__1080__最终原声版.mp4`。说明链接到对应的480测试片和1080下载版，记录原配音来源及本地合成/同步检查，不覆盖上述文件。
- 已下载到临时工作目录时，可用 [scripts/archive_result.py](../scripts/archive_result.py) 复制归档；脚本保留原件、防止覆盖与重复归档，并生成同名 `_说明.md`。不得把本次720P首版伪标为480测试。时间使用北京时间。

```powershell
python -X utf8 "<skill>/scripts/archive_result.py" --source-video "<原视频.mp4>" --result "<已下载成片.mp4>" --refs "<商品图目录>" --prompt-file "<实际提交提示词.txt>" --review-file "<本次检查.md>" --setting "480原生" --stage "测试01" --product "<货号-颜色>" --model "<实际模型>"
```

- 说明记录：原视频路径、商品图目录和实际引用列表、目标材质及依据、画布/节点、模型、测试阶段、实际UI设置、实际输出尺寸/时长/帧率、提示词、检查结论与问题时间点，以及本次和累计算力点数（预计、实扣、退款、净消耗和核验状态）。未知数据明确写未核验；不能由UI选项推定实际输出参数。
- 等下载临时扩展名消失且文件大小稳定，检查视频可解码再交付。文件名/说明仅备注，不烧录文字到成片，不覆盖或改动原视频和商品图。
- 归档复制先写同目录随机`.partial`、核对SHA256再发布正式名称；失败只清理本次暂存，不覆盖同名文件。说明/JSON在视频后写入，三者不是整体事务；脚本返回错误时，即使视频存在也要核对侧文件，不宣布完整归档成功。重复调用应按内容识别已有归档，避免无意义复制。


## 一致性检查与交付

先读 [quality-check.md](quality-check.md)，抽帧覆盖各镜头并观看关键动作，比较商品图和原片。重点检查目标商品是否同款、是否还原实际结构、是否有旧物体重现、跨帧漂移、错误遮挡和无关画面变化。黑场、白闪、绿边等可疑片段先对照原片，不把原有转场误报为生成错误。

在原视频同目录的说明中写 **通过 / 有瑕疵 / 不通过** 及证据。480测试可判断整体结构和动作，但细小logo/纹理看不清应写待1080复核，不能判为精确一致。480审核通过且本任务最新授权允许时，按上述流程做1080，下载后独立给出正式结论；任务禁止新增生成时保留现有480与审核边界，不再提交。发现严重换错款、变形或穿模则标不通过，保留失败版本并说明，不以“生成成功”替代质量验收。

交付以 **1080最终原声版** 为主要文件，包含对应的480测试片、1080下载版、同目录说明链接、各阶段关系、画面一致性及原配音同步结论；未到达的阶段明确说明原因。保留画布素材、连接线和结果。只在用户明确要求维护技能时更新本技能，不自行写入其他记忆。
